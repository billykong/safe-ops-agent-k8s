### Reading the overhead numbers

- **Platform and baseline changed on 2026-10-09; compare absolute times across runs, not only ratios.** gVisor now runs on its KVM platform (P1 README finding 32; earlier reports used systrap), and since the same host restart every process on the node has Speculative Store Bypass Disable forced (`Speculation_Store_Bypass: thread force mitigated`), runc containers included. In the earlier runs runc's seccomp filter opted out, so runc's own times grew (pure-Python loop about 252 -> 381 ms, fresh Python about 18 -> 34 ms) and every ratio against runc moved with it.
- **The pure-Python loop: gVisor now beats runc.** User code makes no syscalls in that loop; the difference is SSBD. runc pays it now. Under KVM, gVisor's application code runs in the guest, and its time (about 257 ms) is what runc took before it paid SSBD, consistent with the host's per-process mitigation not applying there. Under systrap it was the other way round: gVisor paid SSBD (about 404 ms) and runc didn't. Kata's guest kernel runs without the mitigation either way.
- **A tight CPU limit roughly doubles gVisor's overhead** (measured under systrap). At the template's 500m limit, the ratios were about twice the 2-CPU ones: `getppid` 5-9x, `stat` 9-10x, small files 8-9x, loopback TCP 2.2-2.4x. The Sentry's work is charged to the pod's CPU quota alongside the user code, so a small quota throttles gVisor sandboxes more than runc ones. Size sandbox CPU limits with this in mind.
- **Kata: syscalls and the network stack beat runc; shared files are the cost.** Inside the VM, user code makes ordinary syscalls into the guest's own Linux kernel, with no trap to a user-space kernel, and the guest kernel runs without the host's speculative-execution mitigations (guest: Spectre v2 and SSB `Vulnerable`; WSL2 host: retpolines, STIBP, SSBD). The guest holds only this sandbox's code, and the host keeps its mitigations at the VM boundary. `/tmp` is a host directory shared into the VM over virtio-fs, so small-file creates and unlinks and reads pay a round trip to the host per operation; Kata documents a memory-backed `emptyDir` as a tmpfs inside the guest, which should avoid that (not measured here). Cold start is the slowest of the three (a VM boots), so the warm pool matters even more.
- **Syscalls, file metadata and the network stack** are where gVisor's design costs: each syscall is handled by the Sentry (under KVM, an exit from the guest, which under nested virtualization costs more than systrap's trap: 100k `getppid` 117 ms vs 83 ms under systrap, 50k `stat` 1.1 s vs 0.53 s), file operations go through gVisor's own VFS before reaching host files, and the TCP stack is gVisor's own netstack. Process creation went the other way: under KVM a fresh Python start took 46 ms (92 ms under systrap) and 50 spawns 155 ms (285 ms), so the agent's round trip for an empty run dropped from about 98 to 52 ms. Workloads that import many modules or call many syscalls pay the most; the empty-run row is the floor for every agent run.
